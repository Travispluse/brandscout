# Name Customer-Visible Files Before Launch

File names look like housekeeping until somebody outside the team sees them.

A prospect downloads `Northline_Sales_Deck_FINAL_v8.pdf`. A customer forwards `export.csv` to their manager. A partner uploads `fieldops-beta-logo.png` to a directory. A journalist saves `founder-headshot-oldco.jpg`. A buyer receives a proposal named `pricing-new-new.pdf`. None of those files may contain the wrong copy inside the document. The file name alone can still make the brand feel unfinished.

Customer-visible file names are tiny brand surfaces. They appear in inboxes, browser download shelves, shared folders, Slack previews, CRM attachments, press kits, procurement portals, customer wikis, and search results for public files. They are also easy to ignore because teams treat them as local artifacts, not launch copy.

This article is narrower than a [brand asset handoff sheet](/blog/brand-asset-handoff-sheet-before-launch), which tracks ownership and access. It is also different from a [screenshot brand safety pass](/blog/screenshot-brand-safety-before-launch), which checks what is visible inside images. This checklist is about the names of the files people save, forward, upload, and cite after your brand goes public.

## List The Files That Can Leave The Team

Start with files that might be downloaded, attached, exported, or shared during launch week.

Do not only check the polished press kit. Look at product-generated files, sales attachments, support downloads, partner packets, and files sitting behind public links.

| File type | Where it may travel | Brand risk |
| --- | --- | --- |
| Sales deck PDF | Prospect follow-ups, investor intros, partner emails | Old product name or "final v12" looks amateur |
| Press assets | Journalist folders, launch directories, media pages | Wrong logo, founder, or category gets copied |
| Product CSV export | Customer reports, internal customer wikis | Generic `export.csv` feels disposable |
| Screenshot PNG | Help docs, social posts, app listings | Staging names or customer data leak through filename |
| Invoice or quote PDF | Buyer inboxes, finance systems | Legal name and public brand relationship is unclear |
| One-page overview | Procurement portals, forwarded emails | Old tagline or modified domain becomes the remembered label |
| Demo data download | Sales trials, customer onboarding, webinars | Sample file exposes internal naming or private context |

The goal is not to rename every internal draft. The goal is to find the files a customer, partner, investor, candidate, journalist, or search engine could reasonably see.

If the asset list is still unclear, build the [launch press room source of truth](/blog/launch-press-room-source-of-truth) first. That gives you the public files outsiders are allowed to copy. Then use this file naming pass to make those files look intentional wherever they appear.

## Separate Working Names From Public Names

Teams need messy working names. That is fine.

Designers need drafts. Founders need notes. Sales may need a custom deck in progress. Product may need exports while testing. The mistake is letting working names become public names by accident.

Use two zones:

| Zone | Purpose | Filename standard |
| --- | --- | --- |
| Working | Internal drafts, unresolved reviews, temporary exports | Can include owner, rough version, or task context |
| Approved public | Files customers or partners may see | Uses the final brand name, clear asset type, and clean status |

For example:

| Working filename | Public filename |
| --- | --- |
| `northline-investor-deck-maya-edits-v6.pdf` | `northline-investor-overview-2026-08-14.pdf` |
| `fieldops-screenshot-new-flow.png` | `northline-scheduling-workspace.png` |
| `homepage-copy-final-final.docx` | `northline-launch-copy-reference.pdf` |
| `export-test.csv` | `northline-jobs-sample-2026-08-14.csv` |

The public file name should not expose review history, internal debate, old names, private customers, or the fact that the team was scrambling yesterday.

This is where a [brand name style sheet](/blog/brand-name-style-sheet-before-launch) helps. It tells people how the name should be written, shortened, capitalized, and paired with modifiers before anyone starts inventing filename rules from memory.

## Build One Small Pattern

A file naming system does not need to be complicated.

Use a pattern that answers the questions a recipient actually has:

```text
brand-asset-audience-or-context-date.ext
```

Not every file needs every field. Use only the pieces that add clarity.

| File need | Pattern | Example |
| --- | --- | --- |
| Evergreen public asset | `brand-asset.ext` | `northline-logo-primary.png` |
| Audience-specific deck | `brand-asset-audience-date.ext` | `northline-overview-investors-2026-08-14.pdf` |
| Product export | `brand-report-type-date.ext` | `northline-schedule-summary-2026-08-14.csv` |
| Screenshot | `brand-product-area-context.ext` | `northline-scheduling-dashboard.png` |
| Partner packet | `brand-partner-asset-date.ext` | `northline-acme-launch-assets-2026-08-14.zip` |

Keep the rules plain:

- Use lowercase for downloadable file names unless a platform requires otherwise.
- Use hyphens between words.
- Put the public brand name first when the file may leave the company.
- Use dates in `YYYY-MM-DD` format when timing matters.
- Avoid spaces if the file may become part of a URL.
- Avoid `final`, `latest`, `new`, `real`, `use-this`, and private initials in public filenames.

The pattern should be boring enough that people follow it under pressure. If someone has to open a naming policy to rename a PDF before a sales call, the system is too heavy.

## Choose Approved Asset Words

The asset word is the middle of the filename: `deck`, `overview`, `logo`, `screenshot`, `press-kit`, `case-study`, `invoice`, `report`, or `export`.

Choose those words deliberately. They teach people what the file is.

| Weak asset word | Problem | Better direction |
| --- | --- | --- |
| `thing` | Says nothing | `overview` |
| `deck` for every PDF | Hides audience and purpose | `sales-overview`, `investor-overview`, `partner-guide` |
| `image` | Too vague | `logo-primary`, `product-screenshot`, `founder-headshot` |
| `data` | Can sound sensitive | `schedule-summary`, `sample-jobs`, `usage-report` |
| `proposal-new` | Exposes internal status | `proposal-acme-2026-08-14` |

Avoid naming files after internal projects unless customers already know that name. A PDF called `dispatch-engine-overview.pdf` can accidentally make a feature sound like a separate product. A CSV called `ops-unification-export.csv` teaches an internal initiative instead of the customer job.

If the file needs category language, borrow it from the [category language sheet](/blog/category-language-sheet-before-launch). If the file needs a URL, borrow it from the [canonical brand URL checklist](/blog/canonical-brand-url-before-launch). Do not let file names become a side channel where old positioning survives.

## Give Product Exports Real Names

Product exports are easy to overlook because the system creates them automatically.

That is exactly why they matter. Customers may save those files for audits, reporting, finance, board updates, onboarding, support tickets, or internal approvals. A strong product can feel less trustworthy when every download is called `export.csv` or `report.pdf`.

Review the filenames your product generates:

| Export | Weak filename | Better filename |
| --- | --- | --- |
| Schedule CSV | `export.csv` | `northline-schedule-summary-2026-08-14.csv` |
| Invoice PDF | `invoice.pdf` | `northline-invoice-1048.pdf` |
| Usage report | `report_final.pdf` | `northline-usage-report-2026-08.pdf` |
| Contact import template | `template.csv` | `northline-contact-import-template.csv` |
| Demo report | `beta_sample_data.csv` | `northline-sample-jobs.csv` |

Be careful with customer names inside filenames. A file named `northline-acme-payroll-errors.csv` might be useful internally and risky when forwarded. When in doubt, use a neutral identifier, date, report type, or account ID that your product can explain.

This fits naturally beside the [demo workspace brand QA](/blog/demo-workspace-brand-qa-before-launch). Demo accounts, product exports, browser titles, and shared report links all become small proof points that the product is either launch-ready or still wearing its test clothes.

## Make Screenshots And Images Searchable Without Leaking

Image filenames travel farther than teams expect.

They show up in press folders, CMS media libraries, partner uploads, social schedulers, public asset URLs, and sometimes image search. They also sit inside file metadata and downloaded archives long after the source page changes.

Use names that describe the image without exposing private context:

| Image | Better filename |
| --- | --- |
| Product dashboard screenshot | `northline-scheduling-dashboard.png` |
| Mobile app screen | `northline-mobile-job-details.png` |
| Founder headshot | `northline-founder-maya-chen.jpg` |
| Launch social card | `northline-launch-card-1200x630.png` |
| Logo on transparent background | `northline-logo-primary-transparent.png` |

Avoid:

- Old codenames.
- Customer names without permission.
- `screenshot-2026-08-14-at-2-31-44-pm.png`.
- Internal feature labels.
- Joke names from design exploration.
- Claims the page copy does not support.

The [brand link preview QA](/blog/brand-link-preview-qa-before-launch) checks how links unfold in social and messaging apps. File naming is the asset-level version of the same habit: assume the filename may be seen by someone who has no context and no patience.

## Clean Decks, One-Pagers, And Press Files

Decks and one-pagers deserve a stricter rule because they are designed to be forwarded.

If a customer forwards your sales deck to finance, the attachment name becomes the first line of the handoff. If an investor forwards your one-pager to a partner, the filename may be the only stable label in the thread. If a journalist downloads a press kit, those file names may be copied into a publication workflow.

Use names like:

| Asset | Public filename |
| --- | --- |
| Sales deck | `northline-sales-overview-2026-08-14.pdf` |
| Investor one-pager | `northline-investor-overview-2026-08-14.pdf` |
| Partner brief | `northline-partner-brief-2026-08-14.pdf` |
| Press kit archive | `northline-press-kit-2026-08-14.zip` |
| Product overview | `northline-product-overview.pdf` |

If the deck itself still needs review, use the [sales deck brand QA](/blog/sales-deck-brand-qa-before-launch). If outsiders will reuse logos, screenshots, founder photos, or boilerplate, route those assets through the [launch press room source of truth](/blog/launch-press-room-source-of-truth). The filename pass should happen after the contents are approved, not as a substitute for checking the file.

## Name Partner Files For The Person Receiving Them

Partner files often fail because they are named from your team's point of view.

`partner-assets.zip` may be obvious to you. It is not obvious to the partner's marketing lead two weeks later. `northline-acme-launch-assets-2026-08-14.zip` is longer, but it tells the recipient what the file is, who it is for, and whether it is current.

Create partner-ready names for:

- Co-marketing blurbs.
- Logo packs.
- Screenshots.
- Offer sheets.
- Integration setup PDFs.
- Webinar decks.
- Affiliate or referral instructions.
- Marketplace listing assets.

If the partner also needs approved public copy, give them a [partner brand facts sheet](/blog/partner-brand-facts-sheet-before-launch). Do not expect them to infer the correct brand name, category, domain, and file naming pattern from a shared folder full of drafts.

## Retire Bad File Names Before Uploading

Renaming a local file is easy. Renaming a file after it has been uploaded, cached, indexed, embedded, or forwarded is slower.

Before launch, search shared drives, CMS media libraries, public folders, and source repositories for old terms:

- Rejected brand names.
- Old domain modifiers.
- Previous product names.
- Internal project codenames.
- Founder initials in public files.
- `final`, `new`, `copy`, `draft`, and `v2` in approved folders.
- Customer names in examples or screenshots.

This builds directly on the [retire rejected brand names before launch](/blog/retire-rejected-brand-names-before-launch) cleanup. Rejected names do not only appear in body copy. They survive in filenames because nobody treats filenames as copy.

When a file has already been shared publicly, do not quietly upload a second version with a different name and hope people find it. Replace the source link when possible, redirect if the file has a stable URL, and note the correction in your [brand correction queue](/blog/brand-correction-queue-after-launch) if an outside party needs to update it.

## Create One Approved Folder

A naming rule is only useful if people can find the approved files.

Create one launch-ready folder or asset page with a clear boundary:

| Folder | What belongs there |
| --- | --- |
| `approved-public` | Files safe to send, download, upload, or publish |
| `working` | Drafts, comments, experiments, unresolved versions |
| `archive` | Old files preserved for history, not reuse |
| `do-not-use` | Retired files kept only so the team knows what was replaced |

The folder names can be different in your system. The boundary matters more than the labels.

Give one owner authority to move files into `approved-public`. That owner is not responsible for every asset forever, but they are responsible for preventing the shared folder from becoming a drawer of maybes.

For a tiny company, this may be one folder in Google Drive or Dropbox. For a software product, it may be a CMS media library plus a product export rule. For a larger launch, it may be a lightweight digital asset manager. The tool matters less than the rule: if someone grabs a public file, the filename should already be clean.

## Run The Download Test

Do not review filenames only in the folder where you created them.

Test the places where recipients will actually see them:

| Test | What to check |
| --- | --- |
| Download from website | Browser download name is clean and recognizable |
| Attach to email | Attachment name looks professional in inbox preview |
| Forward to another person | Filename still explains the file without your original context |
| Upload to partner portal | Public asset name does not expose draft status |
| Save on mobile | Name is short enough to scan on a small screen |
| Search local downloads | Brand and asset words make the file findable |
| Open from shared drive | Approved version is easy to distinguish from drafts |

This test catches problems that a content review misses. A page button may say "Download the launch kit" while the actual file downloads as `assets-compressed-final2.zip`. A CRM may rename attachments. A product export may strip spaces or uppercase letters. A CMS may preserve the original upload name in the asset URL.

Run the test before the launch copy QA pass closes. Once links are placed in emails, decks, support docs, directories, and ads, the filename is no longer a local detail.

## A Simple File Naming Sheet

You do not need a long policy. A one-page sheet is enough.

| Rule | Approved answer |
| --- | --- |
| Public brand prefix | `northline` |
| Separator | Hyphen |
| Date format | `YYYY-MM-DD` |
| Case | Lowercase for public downloads |
| Approved asset words | `logo`, `screenshot`, `overview`, `press-kit`, `invoice`, `schedule-summary` |
| Words to avoid | `final`, `new`, `draft`, `old`, `beta`, retired names |
| Customer names | Only when approved and useful |
| Public folder | `approved-public` |
| Review owner | Marketing or launch operations |

Put this near the [launch copy QA](/blog/launch-copy-qa-before-launch), not buried in an operations wiki nobody opens. The people exporting files during launch week should see the rule at the moment they need it.

## The File Name Is Part Of The First Impression

Customers do not judge a launch one surface at a time. They see the homepage, download the deck, receive the email, open the invoice, save the report, forward the PDF, and search for the brand later. Each small surface either reinforces the same identity or adds a little doubt.

Before launch, name the files that can leave the team. Use the final brand name. Remove internal history. Give product exports real names. Keep partner and press files clean. Test the download path the way a recipient will see it.

Then use [BrandScout](/) to check the name, domain, and social handle system around those files. A clean brand footprint is easier to trust when even the attachments look deliberate.
